# CLAUDE.md

## Project

Waybill is a multi-tenant shipment tracking and dispatch platform for small carriers: dispatchers
create and manage shipments, drivers update them, and customers follow a public tracking page.
It is a portfolio project for a full-stack Next.js job search, so hiring managers will read the code.
Code quality, clarity and correctness matter more than speed.

## Read first

1. `docs/architecture.md`: system design, state machine, multi-tenancy, decisions log.
2. `docs/implementation-notes.md`: current status, next steps, gotchas, environment notes.

## Stack

Next.js (App Router) + TypeScript strict, PostgreSQL 16 + Drizzle ORM (drizzle-kit migrations, committed),
Better Auth (email/password + organization plugin), Tailwind CSS + shadcn/ui, Zod, Vitest, Playwright.
pnpm is the package manager; Node 22.

## Code layout and rules

```
src/
  app/          routes only: pages, layouts, route handlers, server action wiring
  domain/       pure business logic, no I/O (status machine, tracking codes)
  server/db/    drizzle schema, client, migrations
  server/services/  use cases: auth check -> validation -> transaction -> result
  server/auth/  Better Auth config and session helpers
  components/   UI components
```

- Routes stay thin: they call a service. Services own authorization and transactions.
- Domain code is pure so it is unit tested without a database.
- The organization always comes from the server-side session (`AuthContext { userId, organizationId, role }`),
  never from client input. Every tenant query filters by `organizationId`; cross-org lookups return not found.
- Validate with Zod at every trust boundary (forms, Server Actions, later the public API).
- Status changes: state machine check + optimistic concurrency (`version`) + event insert in one transaction.
  `shipment_events` is append-only (DB trigger rejects UPDATE, DELETE and TRUNCATE).
- Anything with history (users, organizations, shipments) is deactivated, never hard-deleted: foreign keys
  to history are `restrict`.
- Database constraints (CHECKs, composite FKs) complement Zod validation; they never replace it.
- Auth: the real guard is a server-side check (layout or session helper). `proxy.ts` may redirect
  optimistically but is never the only check.
- Cache Components is on: read cookies, headers, `params` and `searchParams` only inside a `<Suspense>`
  boundary; dynamic routes get a `loading.tsx`.
- Importing a module must not require environment variables (e.g. the DB pool is created lazily), so
  `next build` works without a database.

## Working with libraries

- Library versions here are newer than most training data. Build against the installed version:
  Next.js docs in `node_modules/next/dist/docs/` (see `AGENTS.md`), generated code where a tool provides
  it (Better Auth tables via `pnpm auth:generate`, never hand-written). Never code from memory and hope.
- `AGENTS.md` is regenerated by `next dev`; keep it committed.

## Quality bar

- Never skip, weaken or delete a test to make it pass. Fix the code, or report the problem.
- For critical guarantees (triggers, constraints, authorization), prove the test can fail (temporarily
  break the code, see it go red, restore).
- Every commit leaves the repo working: migrations apply and checks pass at each commit, not only at the tip.
- Integration tests run against a real Postgres. The test setup refuses any database whose name does
  not end in `_test`; tests use random ids instead of cleaning up (history cannot be deleted).
- Update `docs/implementation-notes.md` as you go: tick finished items, record gotchas a newcomer
  would trip over.
- If blocked by the environment (network, missing tool), stop and report the exact error. No mirrors,
  alternative registries or other workarounds without the architect's approval.

## Workflow

- The main session acts as architect and reviewer.
- Implementation is delegated to an Opus subagent at medium effort.
- One branch per phase (`phase-N-<name>`), small logical commits.
- Work is split into checkpoints (listed in `docs/implementation-notes.md`). The implementor finishes one
  checkpoint with all checks green and a clean tree, commits, stops and reports. It never pushes.
- The architect reviews each checkpoint, pushes, and confirms on GitHub that new commits are Verified.
- At the end of a phase the architect opens the PR to `main` and merges it after review; no need to ask the user.
- Every implementor report (each checkpoint, and any other hand-back) contains, in this order:
  checkpoint reached, commit list, check results, deviations from the spec, what to review closely,
  an interview note (one notable problem and the alternatives considered), and **context used and
  remaining (approximate %)**.
- Context management: the architect uses the reported context to decide whether the same implementor
  continues or a fresh one takes over from `CLAUDE.md` + `docs/implementation-notes.md`. Below ~25%
  remaining, the implementor stops at the next clean commit boundary, updates
  `docs/implementation-notes.md` with exact status and next steps, and reports instead of continuing.
- The architect keeps this file current: any lasting rule given to an implementor in a message is added
  here at the next checkpoint review, so a fresh implementor never depends on chat history.
- Interview material: the architect records the interview notes in `docs/engineering-notes.md`
  (problem, approach, tradeoffs, at scale, likely questions) and keeps the user's private prep doc in sync.

## Environment

- Postgres 16 is installed but stopped: `service postgresql start`, then create the role and the
  `waybill` / `waybill_test` databases with the SQL in `.env.example`. Copy `.env.example` to `.env`.
  `pnpm test` needs both: its integration project wipes and re-migrates the `*_test` database.
- Playwright: use the preinstalled chromium at `/opt/pw-browsers/chromium`
  (via `launchOptions.executablePath`). Never run `playwright install`.
- Docker is unavailable.
- Installing packages requires the environment's network policy to allow `registry.npmjs.org`.
  `pnpm view next version` should print a version. If installs fail with `ENOTFOUND`, remove
  `registry.npmjs.org` from `NO_PROXY`, `no_proxy` and `npm_config_noproxy` for that command only
  (details in `docs/implementation-notes.md`).
