# Architecture

Waybill is a multi-tenant shipment tracking and dispatch platform for small carriers.
This document records the system design and the reasoning behind key decisions.
It is updated at the end of every phase.

## Users

| Role       | Surface         | Can do                                                                           |
| ---------- | --------------- | -------------------------------------------------------------------------------- |
| Admin      | `/dashboard`    | Everything a dispatcher can, plus manage members and org settings                |
| Dispatcher | `/dashboard`    | Create shipments, assign drivers, change status, view all org shipments          |
| Driver     | `/driver`       | See assigned shipments, update status, share location, capture proof of delivery |
| Customer   | `/track/[code]` | Public, no login. See status timeline and ETA for one shipment                   |

## Stack

- **Next.js (App Router), TypeScript strict** - Server Components for reads, Server Actions for writes.
- **PostgreSQL + Drizzle ORM** - SQL migrations are generated by drizzle-kit and committed.
- **Better Auth** - email/password sign-in, with the organization plugin for tenants, membership and roles.
- **Tailwind CSS + shadcn/ui** - UI.
- **Zod** - validation at every trust boundary (forms, Server Actions, later the public API).
- **Vitest** (unit + integration against a real Postgres) and **Playwright** (end-to-end).

## Code layout

```
src/
  app/                 routes only: pages, layouts, route handlers, server actions wiring
  domain/              pure business logic, no I/O (status machine, permissions, tracking codes)
  lib/                 small shared helpers (formatting, form data)
  server/
    db/                drizzle schema, client, migrations, maintenance (tooling only)
    services/          use cases: auth check -> validation -> transaction -> result
    realtime/          RealtimeBus (Postgres LISTEN/NOTIFY), message schema, SSE stream
    auth/              Better Auth config, session helpers, sign-in/sign-up with rate limits
    seed/              demo data, built on the services
  components/          UI components
scripts/               CLI entry points (seed)
tests/                 integration fixtures and setup, Playwright specs
```

Rule: route files stay thin. They call a service; services own authorization and transactions.
Domain code is pure so it can be unit tested without a database.

## Multi-tenancy

Every tenant-owned table has an `organization_id` column. The organization is always taken from
the server-side session, never from client input. Services receive an `AuthContext`
(`userId`, `organizationId`, `role`) and every query filters by `organizationId`.
Looking up a shipment from another org returns "not found", never "forbidden", so ids cannot be probed.

The database backs this up: `shipment_events` has a composite foreign key
`(shipment_id, organization_id) -> shipments (id, organization_id)`, so an event can never belong to a
different organization than its shipment. CHECK constraints (positive weight, coordinate ranges,
ISO-2 country codes, status changes with a target status) complement Zod validation in services.

## Authentication and sessions

- Sign-up creates the user, then a new organization with the user as `admin`, then signs in.
  A session hook makes the user's organization the session's active organization.
- `AuthContext` is built per request from the session plus the `member` row, so role changes apply
  immediately.
- Access checks are layered: `proxy.ts` redirects requests without a session cookie (optimistic, no
  validation); `requireAuthContext()` in layouts, pages and Server Actions is the real check; services
  require an `AuthContext` argument and filter by its organization.
- Better Auth owns membership and org settings permissions (only admins manage the org). Shipment
  permissions are domain rules enforced in services.
- **Rate limits.** Our Server Actions call `auth.api.*` directly, which bypasses Better Auth's
  HTTP-level limiter, so sign-in and sign-up have their own: fixed-window counters in Postgres
  (`auth_rate_limits`, keys hashed). Sign-in allows 5 attempts per email + IP per 15 minutes
  (cleared by a successful sign-in) and 30 per IP; sign-up allows 10 submissions per IP per hour.
  Attempts are counted atomically before the password is checked, so parallel guesses cannot
  outrun the counter and the response never reveals whether an email exists. The client IP is the
  first `x-forwarded-for` hop, trusting the platform proxy.

## Demo data

`pnpm db:seed` creates "Demo Freight Co" with an admin, a dispatcher and a driver, and 30 shipments
across every status. It uses only the application's own paths: Better Auth for accounts,
`createShipment` (with an injectable clock to backdate bookings) and `changeShipmentStatus` for
history, so seeded timelines obey the same state machine, role and ordering rules as real ones.
Unfinished shipments are promised relative to the seed time, so all but two deliberately overdue
ones are on time.
History cannot be deleted, so a re-run is a no-op; `--reset` re-creates the local dev database.

## Shipment access

Shipment permissions are pure rules in `src/domain/shipment-permissions.ts`, enforced by the services:

| Role       | Create | See and change                     |
| ---------- | ------ | ---------------------------------- |
| Admin      | yes    | every shipment in the organization |
| Dispatcher | yes    | every shipment in the organization |
| Driver     | no     | only shipments assigned to them    |

Every service that reads or changes a shipment builds its `WHERE` clause from one helper,
`visibleShipments(ctx)` in `src/server/services/shipment-access.ts`: the caller's organization, plus
`assigned_driver_id = userId` for drivers. A shipment outside that scope does not match and is
reported as not found, whether it belongs to another organization or to another driver. Creating a
shipment as a driver is the one explicit `forbidden`: there is no record whose existence it could
reveal. A driver can only be assigned if they are a `driver` member of the same organization.

## Services

Use cases live in `src/server/services/`, one file per use case: `createShipment`, `listShipments`,
`getShipment` (with actor and driver names), `changeShipmentStatus`, `getPublicTracking` and
`listDrivers` (for assignment; admins and dispatchers only), plus from Phase 2 `assignDriver`,
`listAssignedShipments` (the driver app's list), `recordLocationPing` and `getShipmentPositions`. Each takes an `AuthContext` argument
(except the public lookup) instead of reading the session, so it runs in tests without Next.js.

- **Expected outcomes are values.** Results are discriminated unions on `ok` and `reason`
  (`validation` with `fieldErrors` keyed by field path, `forbidden`, `not_found`, `conflict`,
  `invalid_transition`). Services throw only for unexpected failures.
- **Input is `unknown`** and parsed with Zod. Schemas coerce strings, because forms and URL search
  params submit strings, and treat blank optional fields as absent.
- **Transactions contain only database work** and are kept short. Validation and permission checks
  happen before the transaction starts.
- **Tracking code collisions** are retried inside the creating transaction with
  `INSERT ... ON CONFLICT (tracking_code) DO NOTHING RETURNING`, so a collision is "no row" rather
  than an error that would abort the transaction (up to 5 attempts, then an exception).
- **Listing** filters by organization (and status), sorts by `created_at DESC, id DESC` (the `id`
  tie-break keeps pages stable), and counts the total with the same `WHERE`. Search matches the
  normalized tracking code exactly, or any part of the reference (`ILIKE`, wildcards escaped).

## Shipment lifecycle

Status is a finite state machine defined in `src/domain/shipment-status.ts`:

```
created ──> picked_up ──> in_transit ──> out_for_delivery ──> delivered
   │            │             │  ^              │
   │            └──────┬──────┘  │              │
   │                   v         │              │
   ├──────────────> exception ───┴──────────────┘ (resume to in_transit or out_for_delivery)
   v                   │
cancelled <────────────┘
```

| From                 | Allowed next                            |
| -------------------- | --------------------------------------- |
| created              | picked_up, exception, cancelled         |
| picked_up            | in_transit, exception                   |
| in_transit           | out_for_delivery, exception             |
| out_for_delivery     | delivered, exception                    |
| exception            | in_transit, out_for_delivery, cancelled |
| delivered, cancelled | none (terminal)                         |

### Event history (append-only)

Every status change writes a row to `shipment_events`. The current status on `shipments` is a
projection of the latest event, kept for fast queries. Both writes happen in one transaction.

- A database trigger rejects `UPDATE` and `DELETE` on `shipment_events` (and `TRUNCATE`, which
  bypasses row-level triggers), so history is tamper-evident even if application code has a bug.
- Foreign keys from `shipment_events` are `ON DELETE RESTRICT`: a cascade would itself be a
  `DELETE`/`UPDATE` of history. Users, organizations and shipments with history are deactivated,
  not hard-deleted.
- `occurred_at` (when it happened in the real world, may be backdated by a driver who was offline)
  is separate from `recorded_at` (when the server stored it).

### Concurrency

Two dispatchers (or a dispatcher and a driver) can change the same shipment at once.
Status changes use optimistic concurrency: `shipments.version` is incremented on every change and the
update is `WHERE id = $1 AND version = $expected`. Zero rows updated means someone else changed it
first; the user gets a clear conflict message and fresh data instead of a silent overwrite.

`changeShipmentStatus` runs in one transaction:

1. Read the shipment within the caller's scope (`not_found` if absent).
2. If `version` differs from the expected one, return `conflict` with the current row. This is
   checked before the state machine, because a transition picked on a stale form is meaningless.
3. `canTransition(from, to)` or return `invalid_transition`.
4. `UPDATE ... SET status, version = version + 1 WHERE id AND <scope> AND version = expected
RETURNING *`. Under READ COMMITTED a concurrent writer blocks on the row lock; once it commits,
   Postgres re-evaluates `version = expected` against the new row, matches nothing, and we return
   `conflict`. This guard, not step 2, is what prevents lost updates.
5. Insert the `status_changed` event with `from_status` from step 1 (safe: the guarded update proves
   the row did not change in between).

In the UI, a `conflict` re-renders the detail page with the fresh shipment and history, and the
status form is rebuilt on the new `version`, keeping what the user typed, so retrying is deliberate
and informed.

## Tracking codes

Format `WB-XXXX-XXXX`, using Crockford base32 (no I, L, O, U, so codes are easy to read aloud and type),
generated from `crypto.getRandomValues`. 40 bits of randomness: not sequential, not guessable by
enumeration. Unique index in the database; on the rare collision the insert retries with a new code.
User input is normalized before lookup: case, spaces and dashes are ignored, the `WB` prefix is required,
and Crockford look-alikes are mapped (I and L read as 1, O reads as 0).

## Public tracking page

`/track/[code]` is public. It exposes only a safe projection: tracking code, status, timeline (type,
status entered, time, city-level location, public note), origin/destination city and country, and
the promised delivery time. `getPublicTracking` selects an explicit column list, so new columns stay
private by default, and a test asserts the exact key set so an accidental addition fails loudly. It never exposes recipient email, internal
notes, driver identity, or internal ids. Pages are `noindex` because tracking data is private to the
people who hold the code. Unknown and malformed codes get the same not-found page.

## Phase 2: live tracking

Phase 2 adds the driver's side and live updates. Each part starts with the architect's design,
followed by what was built where it refines or differs from it.

### Driver app

- `/driver` is a mobile-first surface for drivers: their assigned shipments (built on
  `visibleShipments`) and big-button status changes built on `statusOptionsFor("driver", ...)`.
- After sign-in, drivers land on `/driver` and staff on `/dashboard`. A driver who opens
  `/dashboard` is redirected to `/driver`. Each surface still runs its own server-side check.
- Dispatchers reassign drivers from the detail page through an `assignDriver` service. It writes a
  `driver_assigned` event (internal history), and the driver must be a member of the same
  organization with the `driver` role.

As implemented (checkpoint 1):

- **Landing and guards.** `homePathFor(role)` is a pure domain rule. Sign-in resolves the new
  session's `AuthContext` from its session row and redirects to that home. Each surface's layout
  and pages call `requireAuthContextOn(surface)`, which redirects anyone on the wrong surface;
  `proxy.ts` still only checks that a session cookie exists.
- **Driver list.** `listAssignedShipments` is `visibleShipments(ctx)` plus "assigned to me".
  Active shipments come first, by earliest promised delivery, then the 10 most recently finished.
  Each card leads with the next stop (pickup before collection, delivery after) and flags overdue
  deadlines.
- **Status changes** use the same Server Action as the dashboard, so conflicts, validation and
  every other result are handled identically. The buttons come from
  `statusOptionsFor("driver", status)`, so drivers are never offered a cancellation.
- **Assignment is a versioned change.** `assignDriver` follows the status-change recipe: read in
  scope, version check, guarded `UPDATE ... version = version + 1`, event insert, one
  transaction. Bumping the version means an assignment invalidates open status and assignment
  forms. That is intended, since the shipment changed under them. Delivered and cancelled
  shipments keep their driver (`closed`). Re-assigning the current driver is rejected, so every
  `driver_assigned` event is a real change. The event has no status, and its `metadata` holds
  `fromDriverId` and `toDriverId`.
- **Event-time ordering** for status changes compares against the latest _status_ event only, so
  an assignment never blocks a driver's legitimately backdated update.

### Location telemetry is not history

Location pings are high-volume telemetry, not meaningful events, so they stay out of
`shipment_events`:

- `location_pings` is an append-only history of positions, with a `bigserial` id, organization,
  shipment, driver, lat/lng, accuracy, device time (`recorded_at`) and server time (`received_at`).
  Index: `(shipment_id, recorded_at desc)`. Pings older than 30 days are purged daily
  (decision 48).
- `shipment_positions` holds one row per shipment with its latest known position. It is upserted
  in the same transaction as the ping. This is the hot query for maps, and it never touches
  `shipments.version`, which is reserved for status concurrency.
- `recordLocationPing` accepts pings only from a driver, only for a shipment assigned to them,
  only while the shipment is active (picked_up, in_transit or out_for_delivery). It throttles to one
  accepted ping per shipment every 10 seconds; pings inside the window are acknowledged and dropped.
  Device times more than 5 minutes in the future are rejected, and stale pings older than the latest
  position do not move it.
- Tenant consistency gets the same composite foreign key pattern as events.

As implemented (checkpoint 2):

- **Throttle as a conditional upsert.** `shipment_positions.updated_at` is the server time of the
  last accepted ping. The upsert's `ON CONFLICT ... DO UPDATE ... WHERE updated_at <= now - 10 s`
  is the only throttle check: Postgres serializes concurrent upserts of one row and re-evaluates
  the condition against the committed row, so exactly one of several parallel pings is accepted.
  Only when the upsert returns a row is the ping inserted, in the same transaction. A throttled
  ping returns `{ ok: true, accepted: false, reason: "throttled" }` and writes nothing.
- **Late pings** are stored and count for the throttle, but per-column `CASE` expressions keep the
  position with the newest device time.
- **Status races.** The shipment row is read `FOR SHARE`, so a status change waits for an in-flight
  ping and a ping is never accepted after the shipment left the road.
- **Mutability.** A trigger rejects `UPDATE` on `location_pings` (a recorded fix is never
  corrected), but `DELETE` stays allowed for the retention purge, unlike `shipment_events`.
- **Snapshot.** `getShipmentPositions(ctx, { shipmentIds? })` returns the latest position of every
  unfinished shipment in the caller's scope (`visibleShipments`), including `exception`, where the
  last known position matters most. Delivered and cancelled shipments drop off.
- **Driver app.** "Share my location" appears only while the shipment is on the road and is off
  until the driver switches it on. The client sends the newest `watchPosition` fix through a Server
  Action at most every 10 s and stops on switch-off, on leaving the page, when the shipment leaves
  the road (the control unmounts) and when the server answers that the shipment is inactive or no
  longer theirs. (In demo mode the position is simulated on the server; see "Demo mode".)
- **Confirm step.** Delivered and cancelled ask for confirmation in an alert dialog in both
  surfaces before the form submits. It guards against slips, not a trust boundary, so it is
  client-side only.

### Public projection rules

- Exact coordinates are never public. The tracking page shows city-level progress only.
- The public timeline includes only customer-facing event types (`created`, `status_changed`).
  Internal events such as `driver_assigned` are filtered out with an explicit allow-list
  (`PUBLIC_SHIPMENT_EVENT_TYPES` in the domain, applied in the query), and tests cover it.

### Realtime: invalidation signals, not a replayed event log

The dashboard, detail page, driver app and map update without reloads. The design treats realtime
messages as hints that data changed, not as the data itself:

- **Signal source.** Services call `pg_notify('waybill_events', payload)` inside the same
  transaction as the write. Postgres delivers the notification only on commit, so rolled-back writes
  never announce themselves. The payload is small JSON (organization id, shipment id, kind, and for
  pings the new position), well under the 8000-byte limit.
- **Fan-out.** Each server instance holds one dedicated `LISTEN` connection and fans messages out
  in-process to its SSE clients. SSE (`text/event-stream` from a route handler) fits because traffic
  is server-to-client only, and `EventSource` reconnects automatically.
- **Scoping.** Every SSE connection is authenticated with `requireAuthContext()`. Messages are
  filtered to the connection's organization, and for drivers to their assigned shipments, before
  anything is written to the stream. Tests prove another organization's events never reach a stream.
- **Reconnects.** No `Last-Event-ID` replay. On (re)connect the client re-fetches the current state
  (`router.refresh()` for server-rendered pages, a positions snapshot endpoint for the map). Because
  messages are invalidations, missing some while disconnected loses nothing.
- **Hosting constraint.** `LISTEN` needs a direct Postgres connection: transaction-mode poolers
  (PgBouncer, Neon's pooled endpoint) do not support it. The listener uses a separate
  `DATABASE_DIRECT_URL`, and normal queries keep the pooled URL. Serverless functions have a maximum
  duration, so the stream closes itself before that limit and the client reconnects.
- **Abstraction.** A small `RealtimeBus` interface, so the Postgres implementation could be replaced
  by a hosted pub/sub (Ably, Pusher, Supabase Realtime) at scale without touching services or UI.

As implemented (checkpoint 3):

- **Messages** (`src/server/realtime/messages.ts`) are a Zod discriminated union:
  `shipment_changed` (organization, shipment, `assignedDriverId`, `previousDriverId`, reason
  `created | status | assignment`) and `position` (organization, shipment, driver, lat/lng, device
  time). About 250 bytes. They are validated before `pg_notify` (an invalid message throws and
  fails the write: a programming error) and again on receipt, where anything malformed is
  dropped with a log line; anyone with database access can `NOTIFY` the channel.
- **Publish points.** `createShipment`, `changeShipmentStatus`, `assignDriver` (with the previous
  driver, so their app drops the shipment) and `recordLocationPing` (only when the position moved;
  throttled and late pings stay silent) call `announceShipmentChange` / `announcePosition` inside
  their existing transactions. Rejected writes return before publishing.
- **Listener lifecycle** (`PostgresRealtimeBus`). One `pg.Client` (not a pool connection) per
  instance, `application_name = waybill-realtime`, TCP keepalive, created on the first subscriber.
  If it drops, it reconnects with jittered exponential backoff (250 ms to 10 s). After the last
  subscriber leaves it stays connected for 30 s, then closes: streams reconnect every few minutes
  and on page loads, and closing on every short gap would mean a new connection and `LISTEN` each
  time.
- **`resync` is a bus signal, not only a client concept.** A subscriber receives `resync` when its
  subscription is live (immediately if the connection already listens, otherwise once `LISTEN`
  completes) and again after every reconnect. The stream forwards it, and clients re-fetch on it.
  This refines "re-fetch on (re)connect": the browser's `open` event only means the HTTP response
  started, possibly before `LISTEN` is active, so re-fetching then could miss a change committed in
  between. The first `resync` is the moment from which delivery is guaranteed.
- **Stream** (`GET /api/realtime`, `createRealtimeStream`). 401 without a session (an API does not
  redirect: `EventSource` would follow it to HTML and fail silently). The session is read from
  `request.headers` (`getAuthContextFromHeaders`, shared with `getAuthContext`), so tests invoke
  the handler with a constructed `Request`. Each message passes the pure `isVisibleTo(viewer,
message)` (organization; for drivers, assigned or previous driver) and is projected by
  `toClientEvent` to `{ kind, shipmentId, reason }` or `{ kind, shipmentId, lat, lng, recordedAt }`,
  so no organization or user ids reach the browser. It sends `retry: 3000`, a comment heartbeat
  every 25 s, closes itself after `REALTIME_STREAM_SECONDS` (default 270, clamped to 5-290) under
  `maxDuration = 300`, drops a client with more than 500 queued events, and unsubscribes on every
  exit path. `Cache-Control: no-cache, no-transform` keeps Next's gzip from buffering the stream;
  `X-Accel-Buffering: no` does the same for nginx.
- **Client.** `RealtimeProvider` in the dashboard and driver layouts owns one `EventSource` per tab
  (layouts stay mounted across client navigations). `connectRealtime` (framework-free, unit
  tested) reports `connecting / live / reconnecting`, waits 5 s before showing `reconnecting` so
  the routine reconnect does not flash, and reopens with backoff (2 s to 60 s) when the browser
  gives up (a 401 or 502). `LiveRefresh` on each server-rendered page calls `router.refresh()` on
  `resync` and on relevant `shipment_changed` events (that shipment on detail pages, any on lists),
  coalesced over 300 ms without extending the window, so bursts cause one refresh and a steady
  stream still refreshes. Positions never refresh a page; `useLivePosition` applies them in place
  (the staff detail page's "Last seen" line now, the map in checkpoint 4). A page hidden by Next's
  Activity does not listen, so it refreshes when shown again.
- **Unsaved input.** The status and assignment forms are keyed by `version`, so a refresh that
  brings a new version remounts them and wipes what the user typed. They carry
  `data-unsaved-guard`; while any guarded field differs from its rendered default, a refresh is
  deferred and a notice (pinned to the viewport bottom, a polite live region) offers "Show latest".
  The deferred refresh runs once the input is cleared; a submit drops it, because the action
  re-renders the page (success or conflict). Unguarded forms (the list's search box) keep their DOM
  values across a refresh. The version check remains the guarantee: a user who submits on stale
  data gets the conflict flow, as before.
- **Live indicator.** A pill in both headers: coloured dot plus short text ("Live",
  "Reconnecting…", "Connecting…"), and a `role="status"` region with the full wording.

### Hosting the realtime path

- **Direct connection.** `LISTEN` holds session state, so it needs a direct connection. On Neon,
  `DATABASE_URL` is the pooled endpoint (`-pooler` host) and `DATABASE_DIRECT_URL` the direct one;
  with PgBouncer in transaction mode, point it at Postgres itself. Locally it falls back to
  `DATABASE_URL`. Every running instance holds one such connection while it has viewers.
- **Vercel.** Each open stream is a running function invocation for up to 270 s. With Fluid compute
  (the default), one instance serves many concurrent invocations, so many streams share one
  `LISTEN` connection; without it, every stream would be its own instance with its own
  connection, which does not scale beyond a demo. Streams are billed while open (active CPU is
  low, they mostly wait). `maxDuration = 300` is the Fluid compute default on every plan and the Hobby maximum (Pro allows up to 800 s; see [Vercel's duration docs](https://vercel.com/docs/functions/configuring-functions/duration), checked October 2026); a plan with
  a lower limit needs `REALTIME_STREAM_SECONDS` lowered below it. Instances that go idle are
  frozen, which simply ends their streams; clients reconnect and resync.
- **HTTP/1.1.** Browsers allow about six connections per origin over HTTP/1.1, and each tab's
  stream takes one. Vercel serves HTTP/2, where this does not apply; a self-hosted HTTP/1.1 setup
  with many open tabs would want HTTP/2 in front.
- **At scale.** `NOTIFY` takes a database-wide lock at commit for transactions that notified, so
  very high write rates serialize commits. Before that point, the `RealtimeBus` interface allows a
  hosted pub/sub; publishing from inside the transaction would then need an outbox table (written
  in the transaction, relayed after commit) to keep "only committed writes are announced".

### Map

- MapLibre GL, loaded client-side only, with OpenFreeMap vector tiles (OpenStreetMap data, no API
  key, with attribution). The public `tile.openstreetmap.org` servers are not used because their usage
  policy forbids this kind of app traffic.
- The dashboard map shows all active shipments, and the detail page shows a small map with the
  route and the latest position. The public page has no map.
- End-to-end tests must not depend on tile servers: Playwright blocks tile requests and asserts on
  markers and data, not on rendered tiles.

As implemented (checkpoint 4):

- **Basemap.** OpenFreeMap's "positron" style: pale and nearly colourless, so the status colours
  of the markers are the only colour on the map ("liberty" paints parks and water in the same
  greens and blues as the statuses). Attribution comes from the style and stays expanded at
  every width, as OpenStreetMap's licence asks.
- **Client-only.** MapLibre is imported only by two canvas components loaded with `next/dynamic`
  (`ssr: false`), so it is absent from the server bundle and loads after the page (about 290 KB
  gzip of JS plus its tile worker, on the map and detail pages only). The page around it,
  including the text list, is server-rendered.
- **Placement.** `/dashboard/map` is its own route, switched to from the list with a "List | Map"
  control (and the header). The list is paginated and shows every shipment; the map shows all
  unfinished shipments with a position. Separate URLs keep both shareable and keep MapLibre out of
  the most visited page.
- **Data and live updates.** The page passes `getShipmentPositions` (now with the destination) to
  `FleetMap`. Position events move markers in place (`mergeFleet`: the newest device time wins
  between snapshot and event). Everything else is a page refresh through `LiveRefresh`: on
  `resync`, on any `shipment_changed` (a delivered shipment drops out of the snapshot, so its
  marker goes), and on a position for a shipment the snapshot does not know yet (its first ping).
  This replaces the planned snapshot endpoint: the client derives its state from the snapshot
  prop, so `router.refresh()` reaches it, and resync, coalescing and hidden-page handling stay in
  one place.
- **Markers** are DOM elements (buttons with an accessible label such as "WB-…, In transit, to
  Antwerp"), coloured by the status tone shared with the badges (`statusTone`). A new fix glides
  the marker over 800 ms with an ease-out, or jumps under `prefers-reduced-motion`. Clicking a
  marker, or the "Show on map" button of its list entry, opens a popup (tracking code linking to
  the detail page, status, destination, "last seen … ago"); Escape or a click on the map closes it.
- **Text first.** Beside the map (under it on a phone) a list of the same shipments with links,
  status, destination, last seen and coordinates, in a stable order (problems first, then by
  tracking code), so it never reshuffles under a keyboard user. The detail page keeps its
  "Last seen" line.
- **Detail map.** Pickup and delivery pins, the route, and the live position marker. Cooperative
  gestures, since it sits in a scrolling page. Since checkpoint 5 the route is the real road route
  (solid) when the fixture has the pair, else a dashed straight line (see "Truck simulator").
- **Lifecycle.** The map is created in an effect and removed in its cleanup, which also runs when
  Next hides the route (Activity), so hidden pages hold no WebGL context.

### Truck simulator

(Refill, added after checkpoint 5 of phase 2: see "Refill" at the end of this section.)

- A script that drives seeded active shipments: it posts pings and status changes as the assigned
  driver through the same services, so the demo map moves.
- Routes come from committed fixtures. A one-off script fetches road geometry for the seed's city
  pairs from a public OSRM server and commits it as JSON, so the simulator follows real roads with no
  runtime dependency. If fetching is not possible, the fallback is great-circle interpolation, which
  is documented as such.

As implemented (checkpoint 5):

- **Seed drafted as data.** `draftDemoShipments(now)` (`src/server/seed/demo-data.ts`) makes every
  random choice of the seed up front, in the original draw order (a seeded database is unchanged);
  `seedDemo` applies the draft through the services. So the fixture script and a unit test can list
  the seed's 29 pickup → delivery pairs without a database.
- **Route fixture.** `pnpm routes:fetch` requests each pair from `router.project-osrm.org`
  (`overview=full`, GeoJSON), one at a time, 1.5 s apart, with a User-Agent naming the project. It
  simplifies each line with Douglas-Peucker at 120 m, rounds to 5 decimals (about 1 m), and pins
  both ends to the exact stop coordinates (OSRM snaps to the nearest road). Result:
  `src/server/routes/road-routes.json`, 60 KB, with OSRM's distance and duration and an ODbL
  attribution. It is excluded from Prettier (one line per route keeps it small and diffable) and is
  never fetched at runtime. A unit test fails if a seed pair has no route. OSRM was reachable, so
  the great-circle fallback was not needed for the fixture.
- **Lookup.** `routeBetween(origin, destination)` (`src/server/routes/road-routes.ts`,
  `server-only`) matches the stops by coordinates (within 1e-4°) and returns
  `{ kind: "road" | "straight", line }`. The detail page passes only that one LineString to the
  client; the public page has no route. UI-booked shipments between other places get the straight
  line. The seed's last positions now sit the same fraction along the road route.
- **Geometry** (`src/lib/route-geometry.ts`, pure): haversine distances, cumulative distances
  along a route, the point at a distance (binary search), and the distance along the route of a
  nearby point (projection onto the closest segment).
- **Core** (`src/server/simulator/truck.ts`, pure): `planTick(state, config, random)` returns the
  actions for one truck and its next state. Defaults: a tick every 12 s (the server accepts one
  ping per 10 s, so a 10 s cadence would be throttled by jitter), 30x time compression, 80 km/h on
  the road and 35 km/h out for delivery: about 8 km per tick, visible at the fleet map's zoom.
  Statuses: `created → picked_up` at the pickup, `→ in_transit` as it sets off, `→
out_for_delivery` within 15 km of the address, `→ delivered` on arrival ("Delivered to
  reception"). In transit there is a 1 % chance per tick of an exception with a public note, at most
  once per truck per run, cleared after 5 ticks. A ping always precedes a status that takes the
  shipment off the road, so the arrival ping lands on the address.
- **Wiring** (`src/server/simulator/simulator.ts`): `createSimulator({ drivers, random, config,
maxShipments, clock, log })`. Each tick re-reads every driver's assigned unfinished shipments
  with the driver's own `AuthContext` (`listAssignedShipments`, `getShipment`,
  `getShipmentPositions`), plans each truck and calls `recordLocationPing` /
  `changeShipmentStatus`, nothing else. Only the distance along each route and an exception
  countdown live in memory; status and version come fresh each tick, so a dispatcher can intervene.
  A refused action (conflict, invalid transition) ends that truck's tick and it is re-planned from
  the fresh state; a throttled ping is a normal outcome (the truck still moved). A truck seen for
  the first time starts from its last position projected onto its route, so restarts continue.
- **Whose exception.** An exception whose latest status event was recorded by the truck's driver
  (the simulator's own, from this or an earlier run, or the seed's) is the driver's to clear; one
  recorded by the office is a hold, left until the office moves it on. Deciding from history
  rather than memory means `--once` runs and restarts never strand a shipment.
- **Script** (`pnpm simulate`, `scripts/simulate.ts`): resolves Demo Freight Co's drivers as
  session-equivalent `AuthContext`s (`resolveAuthContext`, `listDrivers` as the admin), refuses
  any database but `waybill`, `--once`, `--speed`, `--seed`, `--shipments`, `--tick` (at least
  11 s), one log line per action, stops after the current tick on Ctrl+C, and suggests a reseed
  when nothing is left to drive. Assigned shipments still at the sender are picked up, so a
  dispatcher can assign the demo driver to a new booking during a demo and watch it join.

Refill (phase 4a follow-up):

- **Why.** On the hosted demo, trucks move only while someone views the map, and viewing time adds
  up across visitors, so within minutes every seeded truck was delivered and the map stayed empty
  until the nightly reset.
- **Decision (pure).** `planRefill(unfinished, { target, maxPerTick })` in
  `src/server/simulator/booking.ts` returns how many to book: the gap to `target`, capped by
  `maxPerTick`, never negative. Defaults 6 and 2, so an empty fleet refills over three ticks.
  `draftBooking(random, now, pairs)` makes the shipment's values from the simulator's PRNG in a
  fixed order: a city pair, service level, reference, recipient, weight and a promised delivery
  (17:00 UTC, a service-level number of days out, at least two hours ahead, so a booking is never
  born late). `bookablePairs(routes)` limits pairs to the committed road routes of at most 300 km
  (about 40 ticks at the default speed), so trucks follow real roads and deliveries happen while
  someone watches.
- **Wiring.** `createSimulator({ refill: { dispatcher, target?, maxPerTick? } })`, off when
  omitted. After driving, a tick counts the shipments still to drive; if short, it books as the
  dispatcher with `createShipment` (booking time from the injected clock), then assigns the first
  driver with `assignDriver`, using the version `createShipment` returned. Nothing else writes. The
  next tick sees an assigned `created` shipment and picks it up with the existing behaviour. A
  refused booking is logged and ends that tick's refill. `TickReport` gained `booked` (tracking
  codes), and `remaining` includes them, so `pnpm simulate` does not stop right after booking.
- **What counts as unfinished.** The shipments the simulator can still drive: assigned to its
  drivers, with coordinates, not held by the office in an exception. Unassigned or uncoordinated
  shipments (a dispatcher's own bookings, the seed's unassigned ones) do not count, or a busy
  office would starve the demo of moving trucks.
- **Who.** The hosted tick (`getDemoSimulator`) and `pnpm simulate` turn it on by default, booking
  as the seeded demo dispatcher (`resolveDemoDispatcher`, looked up by email on use, as the
  nightly reset recreates the ids). `pnpm simulate --no-refill` and `--target <n>` adjust it.
  Tests that do not pass `refill` are unchanged.
- **Growth.** Delivered shipments stay in history until the nightly reset. The live map and the
  driver's active list read only unfinished shipments (about six), and the shipment list
  paginates, so many refills do not slow or clutter either.

## Phase 4a: deployment (design)

Goal: a live demo URL recruiters can open, built and verified automatically. This section is the
architect's design; the implementation refines it.

### Hosting

- **Vercel** (Fluid compute) runs the Next.js app, importing the GitHub repository through
  Vercel's Git integration. Pushes to `main` deploy to production, and pull requests get preview
  deployments.
- **Neon** Postgres, connected through the Neon integration in the Vercel marketplace. It injects a
  pooled `DATABASE_URL` and a direct `DATABASE_URL_UNPOOLED`, and can create a database branch per
  preview deployment. The app maps the direct URL to `DATABASE_DIRECT_URL` for the realtime
  `LISTEN` connection and for migrations.
- No deploy secrets live in GitHub or pass through anyone's chat: the owner connects Vercel and Neon
  in their dashboards, and the integrations manage credentials.

### Build, migrations and seed

- A `vercel-build` script runs, in order: environment validation, migrations (direct URL), the demo
  seed (a no-op when the demo organization exists), then `next build`. A failed migration fails
  the deploy instead of shipping code against an old schema.
- Migrations run before the new code serves traffic while the old code may still be serving, so
  every migration must be backward compatible with the previous release (expand, then contract in a
  later release). This rule goes into `CLAUDE.md`.
- Runtime environment variables are validated with Zod in one module (`src/server/env.ts`), with
  clear messages naming the missing variable. Validation runs on first use, never at import, so the
  build-time rule (importing must not require env vars) still holds. As built: the module exposes
  groups (`env.database`, `env.auth`, `env.realtime`, `env.demo`), each validated the first time
  it is read, so a script that only touches the database does not need the auth secret; and
  `validateEnv` checks every group at once for the deploy step. The direct URL resolves
  `DATABASE_DIRECT_URL`, then `DATABASE_URL_UNPOOLED` (the Neon integration's name), then
  `DATABASE_URL`, so no manual mapping is needed on Vercel.

### Continuous integration

- GitHub Actions on every push and pull request: format, lint, typecheck, unit and integration tests
  against a Postgres service container, build, and Playwright end-to-end tests (CI installs
  Playwright's own Chromium; the config already falls back to it outside this environment).
- CI only verifies; deploys come from Vercel's Git integration. A failing check is visible on the
  pull request before merge.
- As built (`.github/workflows/ci.yml`): one job, `contents: read`, superseded runs cancelled. The
  production build runs before any environment exists, so the "no env at import" rule is checked
  on every push; tests then get a Postgres 16 service container and a throwaway auth secret.
  Playwright's report and traces are uploaded when the job fails.

### Demo mode (`DEMO_MODE=true` in production)

- **Banner and credentials.** A small banner says this is a demo whose data resets nightly, and the
  sign-in page offers the three demo accounts with one click each.
- **Nightly reset.** A Vercel Cron job (daily, which the Hobby plan allows) calls
  `/api/cron/reset-demo` with `CRON_SECRET`. It wipes and re-migrates the demo database and re-seeds
  it, because history cannot be deleted row by row by design. It refuses unless demo mode is on and
  the secret matches, and the database name guard still applies.
- **Trucks move while someone watches.** Vercel cannot run a long-lived simulator process, and
  per-minute cron needs a paid plan. Instead, while the live map or a shipment page is open in demo
  mode, the client asks `/api/demo/tick` to advance the simulator by one tick. A global throttle in
  Postgres (one tick per 12 seconds, whatever the number of viewers, using the same conditional
  upsert pattern as the ping throttle) means trucks move at the same pace for everyone, and nothing
  runs when nobody is looking. The tick runs the existing simulator core through the real services.
  The endpoint does nothing unless demo mode is on.
- **Visitors' real location is never used.** Anyone can sign in as the demo driver and switch on
  "Share my location", and what that stores is shown to every other visitor on the dispatcher's
  live map. (Found on the live demo: a real ping from another continent appeared on a truck bound
  for Paris.) In demo mode the driver app therefore never calls `navigator.geolocation`: no
  permission prompt, and the client sends the shipment id alone. The control still works, so
  visitors can try the flow: the Server Action goes through `recordDriverLocation`, which in demo
  mode ignores every client-supplied coordinate, accuracy and device time and stores the next point
  along the shipment's road route (the pure `nextSimulatedPosition`, same route geometry and pace
  as the truck simulator, continuing from the last stored position). It still ends in
  `recordLocationPing`, so throttle, scope, history and realtime are unchanged, and a crafted
  request with real coordinates stores a simulated position. The card says "Demo: a simulated
  position along the route is shared. Your real location is never used." Outside demo mode
  nothing differs. The simulator calls `recordLocationPing` directly with positions it computed, so
  the guard sits on the driver app's entry point, not inside the storage primitive.

### As built (checkpoint 2)

- **Auth origin per environment.** `resolveAuthUrls` (`src/server/auth/base-url.ts`, pure):
  `BETTER_AUTH_URL`, else `https://$VERCEL_PROJECT_PRODUCTION_URL` in production and
  `https://$VERCEL_BRANCH_URL` (or `$VERCEL_URL`) in previews, else an error outside Vercel. Better
  Auth's `trustedOrigins` holds every host of the deployment (unique, branch, production, plus the
  explicit URL), so previews and the alias addresses of one deployment all work without
  per-preview configuration.
- **Build.** `pnpm vercel-build` (`vercel.json` names it as `buildCommand`): validate every
  environment group, `migrateDatabase(directUrl)` under an advisory lock, `seedDemo()` only in
  demo mode, `next build`. The plan is a pure function (`buildPlan`). In demo mode the build also
  refuses a database that is not in `DEMO_RESET_DATABASES`.
- **Guards: wipes only.** A database name is checked only where something is wiped. Local tools
  keep their fixed names (`waybill`, `*_test`, `*_e2e`); the hosted reset uses an explicit
  allow-list in the environment (`DEMO_RESET_DATABASES`), because hosts name databases themselves
  (`neondb`), and requires demo mode, the cron secret and the same database behind the pooled and
  direct URLs. Migrations and seeding never depend on a name.
- **Reset.** `GET /api/cron/reset-demo`: 404 unless demo mode, 401 unless `Bearer <CRON_SECRET>`
  (constant-time on digests), then drop and recreate the schemas, migrate (the SQL files are traced
  into the function; the folder is relative to the working directory), seed. Everyone is signed
  out by it: sessions live in the database.
- **Tick.** `POST /api/demo/tick` calls `advanceDemoSimulation`: demo mode, session, demo
  organization (the seeded admin's, never found by name), then `claimDemoTick` (conditional upsert
  on `demo_tick_state`, one per 12 s globally), then one tick of the per-instance simulator, whose
  drivers are re-resolved every tick. The client (`createDemoTicker`) pauses in hidden tabs.
- **Demo UI at request time.** Banner, one-click buttons and ticker render through `DemoOnly`
  (`connection()` inside `Suspense`), so one build serves both modes. The buttons call a Server
  Action that signs in through the normal service (rate limits apply).

### Hardening

- Security headers: `Content-Security-Policy` (allowing OpenFreeMap tiles and workers),
  `Referrer-Policy`, `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, and
  `Permissions-Policy` allowing geolocation only for the app itself. Vercel adds HSTS.
- As built (`src/lib/security-headers.ts`, applied in `next.config.ts` to every path): a static
  CSP, `default-src 'self'`; scripts from this origin plus inline (decision 40); inline styles
  (React `style` props, MapLibre); `connect-src` this origin (SSE stream, Server Actions) and
  `https://tiles.openfreemap.org` (style, tiles, glyphs, sprites); `worker-src 'self'` (MapLibre's
  bundled worker); `img-src 'self' data:`; `object-src 'none'`, `base-uri 'self'`,
  `form-action 'self'`, `frame-ancestors 'none'`. `Referrer-Policy: strict-origin-when-cross-origin`
  (tracking codes in URLs never leave as referrers), `Permissions-Policy` with `geolocation=(self)`
  and camera, microphone, payment and USB off. An e2e spec walks every surface and fails on any
  CSP violation.
- `robots.txt` that disallows the dashboard, driver app and tracking pages; only the landing page is
  indexable. As built, `/api` and the auth pages are disallowed too, and everything else (the
  landing page and its `/_next/` assets) stays allowed.

## Phase 3: integrations (design)

The checkpoint plan is in `docs/implementation-notes.md` ("Next: Phase 3"). This section records the
architect's decisions that the plan leaves open.

### Every integration works without its key

Resend, Vercel Blob and the Anthropic API need accounts the owner adds later. Each integration sits
behind a small adapter interface with a real implementation and a fake one. Without its key a
feature degrades visibly instead of failing: email goes to a stored preview, photo capture is
hidden, AI intake is hidden. Tests always use the fakes, so CI never calls a third-party service.
Adding the key in Vercel turns a feature on with no code change.

### Public API

- API keys are random 32-byte secrets shown once. Only a SHA-256 hash and a display prefix are
  stored. Keys belong to an organization, carry scopes, and authenticate as an `AuthContext` with a
  dedicated `api` role whose permissions equal a dispatcher's, so every service rule applies.
- Responses are explicit projections with key-set tests. Errors use RFC 9457 problem details.
- Concurrency over HTTP: `ETag` is the shipment version. Status changes require `If-Match`
  (`428` without it, `412` on a mismatch).
- Per-key rate limits reuse the Postgres fixed-window counters (decision 11).

#### As built (checkpoint 1)

- **Roles.** `ROLES` stays the three member roles (they are what Better Auth stores and what
  `isRole` accepts). `api` is `API_ROLE`, and `ActorRole = Role | "api"` is the type of
  `AuthContext.role`, so the permission functions accept it and a `Record<ActorRole, ...>` test
  restates every rule for it. Pages and sign-in keep `MemberAuthContext` (`role: Role`), so they
  can still pick a home path or a label without handling `api`. The access-control and
  organization config never mention `api`.
- **Authentication** (`authenticateApiKey`): bearer token, shape check, then a lookup of its
  SHA-256 in the unique `key_hash` index, revoked keys excluded. No constant-time comparison is
  needed: the stored secret is never compared with the presented one, the database matches
  hashes, and an attacker cannot steer a SHA-256 output. The context acts as the key's creator
  (`createdBy`) with role `api`, and only while that creator is still an admin member of the key's
  organization (the same query joins `member`), so removing or demoting an admin switches their
  keys off at the next request. `last_used_at` is written at most once a minute (a read-side
  check plus a conditional UPDATE).
- **HTTP edge** (`src/server/api/`): `apiRoute(scope, handler)` runs, in order, key lookup (401,
  failures counted per client IP, 429 when exceeded), per-key limit (120 per minute, 429), scope
  check (403), then the handler; handlers only translate HTTP to a service call and back.
  `problemFromFailure` maps each service result kind with an exhaustive `switch`.
- **Contract.** Projections are in `projections.ts`; key sets are asserted by integration tests and
  compared with the OpenAPI document by `openapi.test.ts`, which also checks that every route file
  has an operation (and the reverse) and that every `$ref` resolves.
- **Strictness.** Request bodies reject unknown fields (the services' Zod schemas strip them,
  which suits forms). `assignedDriverId` is not accepted: it would expose user ids.
- **Public tracking** through the API reuses `getPublicTracking` and is limited per client IP
  (60 per minute), since there is no key to count against.

### Webhooks without a long-running worker

- Changes write an outbox row in the same transaction (like `pg_notify`), so a delivery exists only
  if the change committed.
- **Where the worker runs (Hobby has only daily cron):** the first attempt runs right after the
  response via Next's `after()`. Retries run in a drain that is globally throttled (the conditional
  upsert pattern) and triggered by later app and API activity. A daily cron is the backstop, and the
  delivery log has a "Resend" button. The backoff schedule is 1 min, 5 min, 30 min, 2 h, 6 h, then
  dead-letter. At scale this becomes a queue (Vercel Queues or QStash) behind the same outbox.
- Signatures are HMAC-SHA256 over `timestamp.body` in a `Waybill-Signature` header, with a 5-minute
  replay window. Each endpoint has its own secret, shown once.
- **SSRF protection:** endpoint URLs must be `https`. The resolved IP addresses must not be private,
  loopback, link-local or metadata addresses, and this is checked at delivery time, not only on save,
  to defeat DNS rebinding. Redirects are not followed, the timeout is 5 seconds and response bodies
  are capped.
- Deliveries are at least once, and every payload carries an event id for receivers to deduplicate.

### Email

- Customer notifications on chosen status changes are sent from the same outbox, with an
  idempotency key per event, the public tracking link and an unsubscribe link.
- In demo mode, email never leaves the system: recipients are whatever visitors type, so sending
  would be an abuse vector. Messages go to the stored preview, which is shown in the UI.

### Proof of delivery

- The signature is captured as vector strokes (small JSON) and stored in the database, so it needs no
  storage account. The photo goes to private object storage (Vercel Blob), with short-lived signed
  URLs for staff only.
- In demo mode, photo upload is disabled (no visitor files are stored) and a sample photo is shown.
  Signatures still work.
- The public page shows "Delivered, signed by <name>" and never the photo or the signature.

### AI intake

- A dispatcher pastes a shipment request email. The model returns structured output, which is
  validated by the same Zod schema as `createShipment` and shown as an editable draft. Nothing is
  ever booked automatically.
- A small, cheap Claude model (see the `claude-api` reference for the current id), with a per-org
  daily cap and a tight global cap in demo mode. Evaluation uses committed fixtures with recorded
  responses, so CI makes no live calls.
- An inbound-email webhook can be added later, once the owner has a mail domain.
